# 仿豆包 AI 助手 · 整体技术方案（路线图）

> 目标：把现在的"AI 聊天终端"一步步升级成类似豆包的全能 AI 助手。
> 本文写给非技术背景的人也能看懂：每个功能先说"用户看到什么"，再说"背后怎么实现"。

---

## 一、现在已有什么（打好的地基）

| 已完成 | 说明 |
|---|---|
| 文字对话（打字机流式） | 回答一个字一个字蹦出来，不用干等 |
| 多轮上下文 | AI 记得本轮对话前面说过什么 |
| 会话管理 | 左侧多个会话，可新建/重命名/删除，重启不丢 |
| 富文本渲染 | 回答里的代码有高亮、可复制；Markdown 格式正常显示 |
| 一键换厂商 | 配置文件改两个值，就能从智谱切到 DeepSeek/通义等 |
| 本地数据库 | H2 文件库自动创建，后续可平滑换 MySQL |
| 容器化部署 | Docker 一条命令起服务 |

**架构一句话**：浏览器（前端页面）↔ Spring Boot 后端（Java，咱们的大管家）↔ 大模型 API（智谱等厂商的"大脑"）↔ 数据库（存聊天记录）。

以后每加一个功能，基本都是这个套路：**前端加个入口 → 后端加个接口 → 接上对应的模型能力 → 存好数据**。

## 二、升级路线图（按优先级一步步来）

### 阶段 1：图片识别 —— 让 AI"看得见"（看图说话）

- **用户看到什么**：聊天框旁边出现 📷 按钮，可以上传/粘贴图片并配一句话，比如"这道题怎么解？"，AI 看图回答。
- **背后原理**：换用带"眼睛"的视觉模型（如智谱 `glm-4.5v` 系列）。图片被转成 Base64 编码（一长串字符）随消息一起发给模型，模型同时"读"文字和图片。
- **要动的地方**：
  - 后端：消息体从纯文本升级为"文本 + 图片"的多模态结构（Spring AI 原生支持 `Media`）；接口接收图片文件并做大小/格式校验（限制 10MB、jpg/png/webp）。
  - 前端：上传按钮、图片预览、粘贴截图支持（Ctrl+V 直接贴图）。
  - 数据库：消息表加一列存图片引用。
- **难度**：★★☆☆☆　这是性价比最高的一步，做完立刻"像个豆包了"。

### 阶段 2：图片生成 —— 让 AI"会画画"

- **用户看到什么**：输入"画一只戴宇航员头盔的橘猫"，几秒后聊天里出现图片，可放大、下载。
- **背后原理**：调用文生图模型（智谱 CogView 系列）。注意它和聊天是**两个不同的接口**——聊天是"流式吐字"，画图是"提交任务 → 等结果 → 返回图片链接"。后端做一张图一般 5~15 秒。
- **要动的地方**：
  - 后端：新增 `/api/images/generate` 接口，负责调画图 API、把返回的图片下载保存到本地（避免外链过期）、以 `image` 类型消息落库。
  - 前端：识别"生成图片"类消息并渲染图片气泡；生成中显示进度动画。
  - 交互设计：怎么触发画画？两种方案——A. 用户点"🎨 画画"模式开关；B. 让聊天模型自动判断（工具调用，见阶段 5）。先做 A，简单可靠。
- **难度**：★★☆☆☆

### 阶段 3：语音 —— 能听、能说

- **用户看到什么**：按住话筒说话 → 自动转成文字发出；回答旁边有小喇叭，点一下 AI"读"给你听。
- **背后原理**：
  - 听（语音转文字，ASR）：录音 → 调厂商语音识别接口 → 得到文字 → 走现有聊天流程。
  - 说（文字转语音，TTS）：把回答文本调 TTS 接口 → 拿回音频 → 前端播放。
- **要动的地方**：前端录音（浏览器 MediaRecorder）、音频播放器；后端两个转发接口；音频文件存本地/对象存储。
- **难度**：★★★☆☆（录音权限、浏览器兼容、音频格式转换有点琐碎）

### 阶段 4：联网搜索 —— 回答不过时

- **用户看到什么**：问"今天有什么新闻"、"最近的油价"，AI 的回答带最新信息，并附上参考链接。
- **背后原理**：给模型外挂一个"搜索工具"。模型判断这个问题需要查资料 → 后端调搜索接口（智谱自带 web_search 工具，或接博查/SearXNG）→ 把搜索结果喂回给模型组织答案。
- **要动的地方**：后端接入搜索 API + 结果摘要；前端渲染"引用来源"卡片。这一步会自然引出**工具调用（Function Calling）**机制——它是阶段 5 的地基。
- **难度**：★★★☆☆

### 阶段 5：智能体与工具调用 —— 从"聊天"到"干活"

- **用户看到什么**：AI 不只会说，还会做：问天气它真去查天气接口；说"帮我算这批数据"它真跑计算；未来可接"查快递""控制智能家居"等插件。
- **背后原理**（Function Calling，仿豆包的核心机制）：
  1. 我们提前"教"模型一批工具清单（每个工具：名字 + 干什么 + 需要什么参数）；
  2. 模型遇到合适的问题时，不直接回答，而是回一句"请帮我调用 xx 工具，参数是 yy"；
  3. 后端真的去执行，把结果还给模型；
  4. 模型基于结果给出最终回答。整个过程用户只看到流畅的一问一答。
- **要动的地方**：后端"工具注册中心"（Spring AI 内置支持）、执行结果的流式串联、前端展示"正在调用 xx 工具…"的过程提示（豆包的"深度思考中"就是这个体验）。
- **难度**：★★★★☆　这是 AI 应用的分水岭，做完它，阶段 6/7 都顺理成章。

### 阶段 6：知识库（RAG）—— 喂给它你的资料

- **用户看到什么**：上传 PDF/Word/笔记，之后问"我上传的合同里违约金是多少"，AI 能精准回答你文档里的内容。
- **背后原理**（检索增强生成）：
  1. 文档上传后切成小段落；
  2. 每段用向量化模型（Embedding）转成一串数字（可以理解为"语义指纹"）；
  3. 存入向量数据库；
  4. 提问时，先按语义指纹找出最相关的几段，连同问题一起交给模型回答。
  - **比喻**：相当于给 AI 配了一个"资料柜 + 图书管理员"，它回答前先去柜子里翻出相关那几页。
- **要动的地方**：文件解析（Apache PDFBox/POI）、Embedding 接口、向量库（起步阶段数据量小，可用简化方案；量大换 pgvector 或 Milvus）、前端文档管理页。
- **难度**：★★★★☆

### 阶段 7：多用户与产品化 —— 从"自己的工具"到"产品"

- 用户注册登录（每个账号只看自己的会话）；数据从 H2 换 MySQL；上云部署（域名 + HTTPS）；用量统计与限流；敏感内容过滤；PWA 让手机像装 App 一样使用。
- **难度**：★★★☆☆（无技术难点，主要是工程量与细心）

## 三、建议的实施顺序

```
现状 ──→ ① 图片识别 ──→ ② 图片生成 ──→ ③ 联网搜索(顺带打通工具调用机制)
                │                              │
                └──→ ④ 语音 ──→ ⑤ 知识库 RAG ──┴──→ ⑥ 多用户/上云
```

- **先做 ①②**：视觉效果最像豆包，且都只依赖"换模型 + 加接口"，风险低。
- **再做 ③**：联网搜索会把"工具调用"机制带进门，为 ⑤（智能体）铺路。
- **语音④、知识库⑤** 可并行推进。
- **最后产品化**。

## 四、贯穿始终的三个原则

1. **模型能力全部走 API，不自研模型**——我们的核心工作是"编排"：把对话、图片、语音、搜索、工具这些能力组合成流畅体验。
2. **每一步都保持"可换厂商"**——所有能力都走 OpenAI 兼容协议或独立配置项，哪家便宜/好用就切哪家。
3. **小步快跑，每步可演示**——每个阶段做完都是"能点能玩"的完整功能，而不是半成品。

## 五、成本速览（以智谱为例）

| 能力 | 模型/接口 | 费用 |
|---|---|---|
| 文字对话 | glm-5.3-flash / glm-4-flash | flash 系列免费或有赠送额度 |
| 图片识别 | glm-4.5v 系视觉模型 | 按图片大小计费，约几厘/张 |
| 图片生成 | CogView 系列 | 约 0.06~0.1 元/张 |
| 语音 | ASR/TTS 接口 | 按分钟计费，价格很低 |
| 向量化 | Embedding 接口 | 按字符计费，极低 |
